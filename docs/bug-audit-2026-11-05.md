## 1. Codex `compacted` 后镜像配对错位，请求与 Token 被系统性重复计入

**2026-11-06 复核**：属实，已修复。新格式优先覆盖其开始后的窗口；无需用压缩前后用量相等来配对。见文首合成 Probe 结果。

**级别**：P0（统计结果系统性错误）
**位置**：`wpf/TokenView.Wpf/Data/Collectors/CodexCollector.cs:405-429`（核心 `:414-421`）

### 触发条件

同一 rollout 文件内出现 `compacted` 事件，压缩请求的 `payload.usage.total_tokens` 与紧随其后的 `event_msg.token_count.info.last_token_usage.total_tokens` 不相等。压缩请求记录的是整段上下文用量，镜像事件记录的是压缩后的小值，二者天然不等。

### 根因

`ResolveMessages` 用一个只前进、不回退的 `mirrorIndex` 逐条配对“新格式 `token_usage_record`”与“旧格式 `token_count` 镜像”：

```csharp
var isMirror = mirrorIndex < newRecords.Count &&
               legacy.Usage.ClientTotal is { } total &&
               newRecords[mirrorIndex].Usage.TotalTokens == total;
if (isMirror) { mirrorIndex++; continue; }
parsed.Messages.Add(CreateMessage(record));
```

一旦某条镜像的总量与当前 `newRecords[mirrorIndex]` 不相等，`mirrorIndex` 就不再前进。此后所有镜像都会与同一条压缩记录比较，全部失败，于是被当成独立请求写入。

### 影响

- 请求数、请求时间口径的输入/输出/缓存 Token、模型分布与项目分布全部膨胀。
- 会话累计总量不受影响（走 `ThreadAggregate` 的累计值），因此与客户端自身统计对账时看不出异常，缺陷会长期潜伏。
- 子智能体在本机 67 个 rollout 文件上按该逻辑做等价模拟：10 个含 `compacted` 的文件多出 9,963 条 legacy 请求；16,007 条真实请求变成 25,993 条消息（+62%）；请求 Token 由 5.60B 增至 9.45B（+68.8%）；单文件最严重 4,717 → 9,155 条（+94%）。本机 37 个 `compacted` 事件 37/37 均不匹配。
- 该结果不是自动化测试，而是按代码分支对真实文件结构的模拟，仍需在数据库副本上用 Probe 复核一次。

### 修复建议

1. 镜像配对不要依赖“当前索引值相等”，改为按 `(response_id, ordinal)` 或按“累计总量单调递增”建立映射；无法一一对应时，保守地以“新格式优先、旧格式仅保留新格式未覆盖的前缀”为原则。
2. `compacted` 事件显式处理：压缩请求与其镜像不参与配对，单独计数并标注来源。
3. 为 `ResolveMessages` 增加合成 fixture：正常配对、值不匹配、压缩、重复通知、累计重置五种形态。

### 验证方式

`Probe copy` 生产库 → `Probe sync <副本> --force codex` → 对比 `Probe totals` 的请求数与请求 Token；同时抽样若干含 `compacted` 的文件，确认请求数不再大于真实 `response_id` 数。

## 2. 全量快照在“本轮解析出 0 个会话”时仍删除历史并推进水位

**2026-11-06 复核**：零产出替换历史属实，已增加事务回滚保护。列名变化不等于查询返回零行，未采用任意比例阈值或自动多轮清空策略。

**级别**：P1（永久数据丢失）
**位置**：

- `wpf/TokenView.Wpf/Data/Usage/UsageStore.cs:209-215`（`pruneMissing` 无条件删除）
- `wpf/TokenView.Wpf/Data/Usage/UsageStore.cs:274-277`（水位按本轮文件集合回写）
- 调用方：`ClaudeCodeCollector.cs:106`、`DshCollector.cs:137-138`、`OpenCodeCollector.cs:86`、`PiDesktopCollector.cs:144`、`WorkBuddyCollector.cs:117`、`CodeArtsCollector.cs:103`、`DevinCollector.cs:135`

### 触发条件

源目录存在、扫描“成功”，但本轮产出的会话集合为空或大幅减少：

- 客户端格式漂移（`type`/`sessionId` 改名、字段类型变化），每行都走“忽略/未解析”分支；
- 环境变量指向一个存在但没有合法日志的空目录；
- 客户端按保留策略清理了全部转录；
- SQLite 查询因列改名返回 0 行（OpenCode、Devin）。

### 根因

`WriteClientSnapshot` 在 `pruneMissing=true` 时先执行：

```sql
DELETE FROM sessions WHERE client = $client;
DELETE FROM source_files WHERE client = $client;
```

再写入本轮结果；`messages` 通过 `ON DELETE CASCADE` 一并删除。随后又用本轮 `files` 回写 `source_files` 的水位（size/mtime）。整个路径没有“解析成功但产出为 0，拒绝替换”的下限保护，也区分不了“源确实被清空”和“解析器看不懂”。

### 影响

- 该客户端全部历史会话、请求、Token 立刻从统计中消失，界面仍显示“已同步”。
- 水位已推进，下一轮因 `IsUnchanged` 跳过，**不会自愈**；只能等解析器修复后手工强制重扫。
- 多个采集器共用这一模式，属于系统性风险，而不是单客户端偶发。

### 修复建议

1. 在 `UsageStore` 层增加保护：`pruneMissing` 且 `sessions.Count == 0`、而库内该客户端已有会话/水位时，拒绝提交并返回可重试错误或“保留旧快照 + 标记异常”。
2. 采集器层增加“零产出/骤降”判定：`FilesSeen > 0 && SessionsImported == 0` 或产出较上轮下降超过阈值时，先写诊断计数，不替换。
3. 对“源确实被清空”提供显式路径（例如连续 N 轮稳定为 0 才允许剪枝），并在设置页提示。

### 验证方式

构造合成目录：先导入 3 个会话，再把所有文件改成不可识别格式，执行一次同步。期望：历史保留、诊断显示未解析行增加、整体标记为可重试或异常，而不是会话数变 0。

## 3. `MergeClientSnapshot` 先删会话再判陈旧，导致外键失败或会话永久丢失

**2026-11-06 复核**：部分属实，已修复陈旧保护失效。原文的外键失败/永久删行推演不成立：删除后查不到旧行，会走插入。

**级别**：P1（部分失败路径的数据丢失/持续报错）
**位置**：`wpf/TokenView.Wpf/Data/Usage/UsageStore.cs:249-260`、`:447-450`、`:695`；调用方 `DshCollector.cs:137-138`、`CopilotCollector.cs:211`

### 触发条件

部分文件失败时走 `MergeClientSnapshot`（DSH 有文件失败、Copilot 的 CLI/Host 源缺失都属于常态），且某个待写入会话命中 `ShouldReplaceSession` 的拒绝分支：

- 新 `EndedAtMs` 早于库内 `updated_at_ms`；
- 新总量为 `NULL` 而库内已知；
- `client_cumulative` 新值小于旧值。

### 根因

```csharp
if (!pruneMissing)
{
    DELETE FROM sessions WHERE client = $client AND client_session_id = $session;
}
summary = summary with { Session = UpsertSession(transaction, entry.Session) };
foreach (var message in entry.Messages) UpsertMessage(...);
```

删除是无条件的，`UpsertSession` 之后才判断陈旧并返回 `SkippedStale`，但返回值没有被检查：

- 会话有消息时：`messages.session_id` 引用已删除的 `sessions.id`（`REFERENCES sessions(id)`，`PRAGMA foreign_keys = ON`），插入抛 `SQLITE_CONSTRAINT`，整个 Merge 回滚，客户端持续报“无法写入用量库”；
- 会话无消息时：没有外键检查，事务直接提交，**会话行被永久删除**，而 `source_files` 水位已在同一事务中前进，下次同步若文件未变化就跳过，损失不自愈。

### 影响

DSH 与 Copilot 的部分失败路径都会命中；表现是“某客户端一直同步失败”或“某会话突然消失且不再回来”，且错误信息指向数据库而非陈旧判断。

### 修复建议

1. 先 `UpsertSession`，仅当结果不是 `SkippedStale` 时才删除旧消息并重写；或者先查询现有会话是否允许替换，再决定是否删除。
2. 删除范围限定为“本轮确实要替换的会话”，不要对每个会话先删后判。
3. 增加“陈旧跳过”计数并在诊断中展示，避免静默。

### 验证方式

在数据库副本上构造“库内会话总量已知、本轮会话总量为 NULL”的 Merge，确认旧会话与消息保留、`SessionsSkippedStale` 增加、同步不报外键错误。

## 4. 请求预聚合按小时桶起点过滤，分钟级范围漏算首小时、多算末小时

**2026-11-06 复核**：属实，已修复。向内取完整桶应使用 ceil(from) / floor(to)，原建议的 floor(from) / ceil(to) 不是向内收敛；边界回查明细。

**级别**：P1（自定义范围数值系统性偏差）
**位置**：`wpf/TokenView.Wpf/Data/Usage/UsageStore.cs:329`、`:381`；`Data/TokenViewDatabase.cs:739`、`:891`、`:100`；`Controls/DateTimeRangePicker.xaml.cs:247-260`

### 触发条件

自定义范围的时间不是整点（选择器允许 `09:30–17:30`），或本机 UTC 偏移为 `:30/:45`（如印度、尼泊尔、部分澳大利亚时区）导致本地零点不对齐 UTC 小时。

### 根因

预聚合把请求写入“所属小时的起点”：

```sql
SELECT (m.created_at_ms / 3600000) * 3600000 AS hour_ms ...
```

查询却直接用调用方传入的精确毫秒过滤桶键：

```sql
WHERE hour_ms >= $from AND hour_ms < $to
```

因此：

- 起始桶 `09:00` 因 `09:00 < 09:30` 被整桶排除，`09:30–10:00` 的请求与 Token 丢失；
- 结束桶 `17:00` 因 `17:00 < 17:30` 被整桶纳入，`17:30–18:00` 的数据被多算。

半小时时区下，“今天”的本地零点对应 UTC 的 `xx:30`，首 30 分钟同样被丢弃。

### 影响

请求数、Token 合计、客户端/模型切片、图表与托盘今日摘要都会偏差，且偏差方向不一致（首尾一漏一多），难以通过总量对账发现。

### 修复建议

1. 查询边界向内收敛到桶边界（`floor(from)` / `ceil(to)`），并对首尾桶回查 `messages.created_at_ms` 做精确裁剪；
2. 或把 `request_hourly` 的键改为“桶序号”并把范围判断放在明细层；
3. 自定义范围在 UI 上明确展示实际生效的半开区间，避免用户以为按分钟精确。

### 验证方式

## 5. 多设备日粒度数据用精确区间过滤，起始边界日整天被丢弃

**2026-11-06 复核**：属实，已修复日范围与跨时区日历标签，原快照 schema 不变。

**级别**：P1（多设备合计偏低）
**位置**：`wpf/TokenView.Wpf/Data/TokenViewDatabase.cs:177`、`:210`；`Data/Peers/PeerUsageReader.cs:80`、`:126`；`Data/Peers/PeerSnapshotBuilder.cs:271-275`；`MainWindow.xaml.cs:956-958`

### 触发条件

设备范围选“全部设备”或单台其他设备，日期范围选自定义且起止时间不是本地零点（例如 `2026-11-01 10:00 — 2026-11-03 12:00`）。

### 根因

peer 快照的 `day_ms` 是**导出方本地零点**；查看方查询时直接把精确的 `from/to` 传给 `day_ms >= $from AND day_ms < $to`：

- 起始日 `00:00 < from 10:00`，该日所有 peer 请求、Token、会话被整天排除；
- 结束日 `00:00 < to 12:01`，整天被计入。

`PeerGranularityDaily` 只控制提示文案，没有把边界扩到本地日界。界面还明确写着“自定义范围的边界日按整日计入”，与实际行为相反。

### 影响

合并后的 Token、请求数、会话数、客户端分布与图表起始日切片少算首日 peer 用量；跨时区时还会整条日序列偏移（导出方与查看方时区差不是整天整数倍时），不只是边界日。

### 修复建议

1. 日粒度查询把 `from` 向下取整到本地日界、`to` 向上取整到次日零点，并在 UI 标注“其他设备按整日计入”；
2. 若要求分钟级精度，peer 快照需增加小时粒度（`peer_request_hourly` 已存在，可在长范围也使用小时表）；
3. 跨时区场景在设备名旁标注“按对方本地日聚合”，避免用户按本机日期理解。

### 验证方式

`probe peer-roundtrip <dbA> <dbB> <folder>` 后，用非零点的自定义范围查询 All 视图，对比 `local + peer` 的期望值；当前首日 peer 恒为 0。

## 6. 畸形 Markdown 可使进程崩溃（未捕获异常与栈溢出）

**2026-11-06 复核**：属实，已增加局部降级与迭代 AST 限制，并验证真实 STA 控件；没有注册全局忽略异常。

**级别**：P0（进程崩溃/拒绝服务）
**位置**：`wpf/TokenView.Wpf/Controls/MarkdownView.cs:73`、`:366-388`；调用点 `AnnouncementWindow.xaml.cs:84`、`SettingsWindow.xaml.cs:301`

### 触发条件

公告或关于页的 Markdown（来自固定镜像，上限 512 KiB）包含：

- 约 128 层嵌套引用块（约 256 字节）或 100×100 管道表格（约 41 KB）：Markdig 0.40.0 抛 `ArgumentException`；
- 约 5,000 层嵌套图片语法（约 45 KB）：`FlattenText` / `AddInlines` 递归 4,800 余层后栈溢出。

### 根因

`BuildDocument` 在依赖属性回调里同步调用 `Markdig.Markdown.Parse`，没有任何 try/catch；`FlattenText` 与 `AddInlines` 对容器内联做无深度限制的递归。仓库没有注册 `DispatcherUnhandledException` / `AppDomain.UnhandledException`，异常直接终止进程；栈溢出连 catch 都无法拦截。

### 影响

- 打开公告/关于页、或 20 分钟自动刷新命中新内容时，应用直接退出；
- 崩溃发生在采集中会硬中断正在进行的数据库写入；
- 内容只来自固定镜像，但镜像内容或代理错误页并非完全可信，且 512 KiB 上限挡不住约 256 字节的嵌套引用。

### 修复建议

1. 在 `MarkdownView` 内包裹解析与渲染，捕获 `ArgumentException` 等并降级为纯文本显示；
2. `AddInlines` / `FlattenText` 增加最大深度（例如 64）与节点数上限，超出即截断并提示；
3. 注册全局异常处理，至少避免静默崩溃；
4. 为嵌套引用、深表格、深内联图片补回归用例。

### 验证方式

用合成 Markdown 分别构造上述三种输入，在 STA 线程构造真实 `MarkdownView`；期望显示降级文本而不是抛异常或栈溢出。

## 7. 单个缺失的缓存字段使整个会话 Token 总量变为 NULL

**2026-11-06 复核**：部分属实。只修复已包含子桶的可确定总量；Kimi 独立缓存缺失仍为未知，不能补零或把已知子集合计冒充完整会话总量。

**级别**：P1（统计漏计且无未知提示）
**位置**：`wpf/TokenView.Wpf/Data/Usage/NormalizedUsage.cs:52`、`:108-116`；`Data/Collectors/KimiCodeCollector.cs:523`；`Data/Collectors/QoderCollector.cs:946`；`Data/Collectors/CodeArtsCollector.cs:216-222`、`:259-269`；`Data/Collectors/RequestBuilder.cs:161-191`

### 触发条件

- Kimi Code：某条 `usage.record` 缺 `inputCacheRead`（含客户端写出的零值占位记录）；
- Qoder IDE：`token_info` 只有 `prompt_tokens` / `completion_tokens`，没有 `cached_tokens`（无缓存命中时常见）；
- CodeArts：会话级 `SumKnownCached` 遇到任一 `cached_tokens = null` 就返回 NULL，而 `input` 回退到含缓存的 `meta.json.input_tokens`。

### 根因

`TokenBuckets.SumWith` 把 `CacheRead` 无条件列为必需项：

```csharp
(Input, true), (Output, true),
(Reasoning, semantics.Reasoning != FieldRelation.NotProvided),
(CacheRead, true),
(CacheWrite, semantics.CacheWriteCountsInTotal),
```

`UsageNormalizer` 已经把 `input` 桶保留为完整 prompt 并标注 `cache_read.missing`，本可确定总量（`input + output`），但 `SumWith` 直接返回 null。`RequestBuilder.Session` 再因任一请求总量未知，把**整个会话**总量置为 NULL。

### 影响

- 本机 Kimi 生产库只读核对：一个含 2,120 条 usage 记录的会话中，1 条零值占位记录缺 `inputCacheRead`，2,119 条消息合计 **304,552,212 Token** 从 `sessions` 侧消失；Kimi 会话合计与消息合计的差额恰为该值（约 2.0%），且 `message_coverage` 仍为 `complete`。
- Qoder IDE 的整会话总量变为 NULL，排行与总账显示 `—`。
- CodeArts 会话级 `input` 含缓存、`cache_read` 为 NULL，本机 4 个会话中 3 个的会话行与请求行相差 8–29 倍。

### 修复建议

1. 对 `FieldRelation.IncludedIn` 的缓存关系，`CacheRead` 缺失不应阻止总量：按 `input + output` 计算并保留 `cache_read.missing` 标注。
2. 对 `Separate` 关系，缺失缓存桶时按“客户端自报总量优先；否则仅用已知必需桶求和”的规则处理，并在 `unknown_relations` 中记录。
3. 会话级汇总区分“字段未知”与“总量未知”，不要把单条记录缺失放大成整会话作废。
4. CodeArts 的 `SumKnownCached` 在空集合时返回 0 而非 NULL，也应一并修正。

### 验证方式

构造含一条缺 `inputCacheRead` 记录、其余记录完整的 Kimi 会话，期望会话总量等于其余记录之和且标注缓存未知；对比当前实现的总量 NULL。

## 8. “清除全部统计数据”不清 `peer_*`，且暂停标志在删除之后才落盘

**2026-11-06 复核**：属实，已统一清除本机及 peer 数据，并先持久化暂停/关闭 LAN、串行等待在途写入。

**级别**：P1（隐私预期与数据一致性）
**位置**：`wpf/TokenView.Wpf/SettingsWindow.xaml.cs:755-799`；`Data/Usage/UsageStore.cs:285-295`；`MainWindow.xaml.cs:212-221`

### 触发条件

已导入过其他电脑的局域网快照（默认开启），在设置页点击“清除全部统计数据”并确认；或确认框停留超过一个同步周期（默认 5 分钟）。

### 根因

设置页复制了一份内联 SQL，只删除：

```sql
messages / sessions / source_files / request_hourly / request_hourly_sessions
```

**没有删除 `peer_devices`**，因此 `peer_*` 的级联不会触发。仓库中已有 `UsageStore.ClearStatistics()` 会删除 `peer_devices`，但没有任何调用方，属于死代码。

此外：

- `SyncService.Current.IsRunning` 只在弹出确认框**之前**检查一次，确认期间 15 秒调度器仍可触发同步，删除后新批次会继续写入；
- `CollectionPaused = true` 在 `DELETE` 与 `COMMIT` 之后才保存，进程若在两者之间退出，重启后会恢复采集。

### 影响

- 提示“统计数据已清除”，但“全部设备”视图仍显示其他电脑的 Token/请求/会话，设备列表也还在；
- 清除竞态会让刚清掉的数据部分回来，或 `DELETE` 等锁 5 秒后报 `database is locked`；
- 与 `docs/architecture.md`、`docs/data-model.md` 规定的清除范围不一致。

### 修复建议

1. 设置页直接调用 `UsageStore.ClearStatistics()`，不要复制 SQL；
2. 先持久化 `CollectionPaused = true`，再等待/阻止新批次，最后执行删除；
3. 确认框返回后重新检查 `IsRunning`，必要时提示“正在采集，已取消清除”；
4. 清除后刷新设备列表与主界面。

### 验证方式

导入一台 peer 后执行清除，检查 `peer_devices` 与四张 `peer_*` 表为空；在确认框停留超过一个同步周期再确认，检查无新数据回填。

## 9. “复制脱敏诊断”实际输出完整本机路径与异常原文

**2026-11-06 复核**：属实，已移除摘要中的路径及任意错误原文，并替换同步/公告兜底错误提示。

**级别**：P1（隐私）
**位置**：`wpf/TokenView.Wpf/SettingsWindow.xaml.cs:541-568`；`Data/Collectors/SyncEngine.cs:58-61`；`Services/AnnouncementService.cs:64`；`AnnouncementWindow.xaml.cs:119`

### 触发条件

设置 · 采集 → 点击“复制脱敏诊断”；或公告已读写入失败时查看错误条。

### 根因

- 诊断摘要逐条拼接 `来源：{path} · {state}`，`path` 是客户端源文件的绝对路径；
- 错误行拼接 `错误：{error}`，`ClientSyncResult.Error` 直接取 `Exception.Message`，文件占用类异常会带出完整路径；
- 公告窗口把 `IOException` / `UnauthorizedAccessException` 的原文直接显示，例如 `Access to the path 'C:\Users\<用户名>\AppData\Roaming\...\settings.json' is denied.`。

仓库内没有任何路径脱敏或替换实现，按钮文案与规范承诺（“不含路径、项目/会话标识或错误原文”）相反。

### 影响

用户通常会把诊断文本贴到 issue 或群聊，等于公开 Windows 用户名、目录结构、客户端使用痕迹；与项目的隐私底线直接冲突。

### 修复建议

1. 诊断输出只保留客户端 key、状态、计数、时间与版本；
2. 路径替换为 `<source>` 或仅保留盘符/根类别；
3. 异常只输出分类（`IOException` / `UnauthorizedAccessException`）与稳定错误码，不输出 `Message`；
4. 为诊断摘要增加一个“不得包含 `C:\`、用户名、会话 ID”的单元测试。

### 验证方式

在 `settings.json` 被占用时复制诊断，检查文本中不出现 `C:\Users`、源目录名或异常原文。

## 10. 更新下载地址白名单未限定同一仓库，任意 GitHub 仓库资产可通过

**2026-11-06 复核**：属实，已限定同仓库 URL 与有效哈希；GitHub 正常 Release CDN 重定向继续允许。

**级别**：P1（更新通道完整性）
**位置**：`wpf/TokenView.Wpf/Services/UpdateService.cs:120-126`；规范对照 `docs/releases.md:74`、`docs/architecture.md:246`

### 触发条件

`latest.json` 被篡改或错误发布，`platforms.windows-x86_64.url` 指向 `https://github.com/<任意组织>/<任意仓库>/releases/download/...`。

### 根因

```csharp
return Uri.TryCreate(url, UriKind.Absolute, out var uri) &&
       uri.Scheme == Uri.UriSchemeHttps &&
       string.Equals(uri.Host, "github.com", StringComparison.OrdinalIgnoreCase) &&
       uri.AbsolutePath.Contains("/releases/download/", StringComparison.Ordinal);
```

只校验主机与路径片段，没有校验 `/Autumn-one/TokenView/` 前缀，且用 `Contains` 而非前缀匹配。`sha256` 也来自同一份 `latest.json`，攻击者只要同时改写 url 与哈希即可自洽。

### 影响

更新通道可被引导到任意 GitHub Release 资产，下载、校验、安装链路全部放行，形成“借更新通道的任意代码执行”。利用前提是 `latest.json` 内容可控（仓库/令牌失守、错误发布、中间人），但项目的安全模型明确要求“只接受同一仓库的 HTTPS Release 资产”。

### 修复建议

1. 白名单改为精确前缀：`https://github.com/Autumn-one/TokenView/releases/download/`；
2. 拒绝重定向到其他主机，或对最终响应 URL 再做一次同样的前缀校验；
3. 对 `latest.json` 的 `sha256` 增加格式校验（64 位十六进制）；
4. 更新包若未来引入签名，校验签名而不是仅校验同源哈希。

### 验证方式

构造 `url` 指向其他仓库的 `latest.json`，期望检查阶段直接拒绝；现有实现会通过并尝试下载。
